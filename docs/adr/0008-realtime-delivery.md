# ADR 0008: Real-time delivery — Socket.io rooms, a token handshake, a snapshot on connect

Date: 2026-09-04
Status: accepted

## Context

M3 puts a guest's order on the kitchen screen in under half a second and then keeps two screens — the board and the guest's phone — agreeing about the same order while both are open. That is a push problem, and the brief names Socket.io for it.

The tempting shape is to move the writes onto the socket too: the cook presses Start, the board emits a `transition` message, the server acks. It is one round trip and it looks tidy. It is also a second front door into the domain. Everything that guards `POST /api/orders` today — the RBAC matrix, Zod validation, the rate limiter, idempotency keys, the audit row — lives in the Fastify request pipeline, and a socket message reaches none of it. Either that stack is re-implemented for messages, or the socket path is quietly weaker than the REST path.

The other half of the problem is where the socket may connect at all. ADR 0004 put the REST API behind the Next.js rewrite so session cookies stay first-party, and it did that precisely because Vercel's rewrites do not proxy WebSockets. The socket therefore cannot ride the same path, and the first-party cookie it would want for authentication is not sent cross-site.

## Decision

**Socket.io pushes, REST mutates.** Every write is still an HTTP request through the proxy, with the whole guard stack in front of it. The socket carries exactly three server-to-client events (`order:created`, `order:updated`, `demo:reset`) and accepts exactly one client-to-server message (`subscribe`); anything else a client sends is ignored. The event map lives in `packages/shared/src/events.ts` and types both ends.

**The seam is an emitter, not a socket handle.** `apps/api/src/lib/order-events.ts` declares `OrderEvents`, a typed `EventEmitter` decorated onto the app as `app.orderEvents`. `createOrder`, `transitionOrder` and the rush generator emit into it after their transaction commits; `apps/api/src/realtime/server.ts` is the only subscriber and the only module that knows a socket exists. Emitting after the commit means no broadcast can roll a write back, and the API tests can assert that a route emitted the right thing without opening a socket at all. It is not full isolation: an emitter dispatches synchronously, so a listener that threw — `publish` re-parses each payload, and a parse can throw — would surface as a 500 on a request whose row is already changed. `publish` is therefore wrapped: a failure to broadcast is logged and the request still answers for the write it made.

**The handshake carries its own credential.** `POST /api/socket-token` sits behind `requireAuthenticated()` on the proxied REST path, where the cookie is first-party and the principal already resolved. It mints an HS256 JWT with header `typ: 'tt-socket'`, subject the user or guest-session id, and a sixty-second expiry, signed with `SOCKET_TOKEN_SECRET` — a secret of its own, not the cookie secret and not `TABLE_TOKEN_SECRET`.

That subject is worth being precise about, because the plan once claimed `guestSessionId` "never leaves the API" and this token contradicts it. The accurate statement is narrower: **`guestSessionId` and `restaurantId` never appear in an order payload and never reach another client; the socket token carries the guest's own session id as its subject, which that browser already holds in its signed `tt_guest` cookie.** It is an addressing identifier handed back to the one browser it belongs to, not a credential — the token's signature is what authenticates, and it expires in a minute. `apps/web/lib/socket.ts` builds the client with an `auth` callback rather than a fixed value, so a fresh token is fetched before every connection attempt, reconnects included; sixty seconds is long enough to complete a handshake and far too short to be worth stealing.

Two properties do real work here. The token is **typed**: `verifySocketToken` passes `typ` to `jwtVerify`, so a table token out of a QR code (`typ: 'tt-table'`) cannot open a socket, and a socket token cannot claim a table. And it is **short-lived**, which is what makes it safe to hand to a browser that will put it in a WebSocket URL's handshake rather than in a cookie the browser protects.

**Rooms are assigned by the server, and a guest's room is its session.** The handshake middleware in `realtime/server.ts` verifies the token, stores the `SocketPrincipal` on `socket.data`, and the connection handler joins the room the principal implies: `kitchen` for staff, `session:<guestSessionId>` for a guest. Clients never name a room, so a guest cannot subscribe to anyone else's feed by any client-side means. Broadcasts go to `kitchen`, plus `session:<order.guestSessionId>` when the order has one — a rush order has none and reaches the kitchen only — and every payload is re-parsed through the public `OrderDtoSchema` on the way out.

The brief and this milestone's plan both named that room `table:<tableId>`. It is wrong, and the final review found it: a table changes hands every sitting, while a socket lives as long as its tab. A phone left open on the last party's order kept receiving the next party's tickets — no identifiers, since every payload is re-parsed, but their order lines. The session is the thing whose lifetime actually matches the subscription, and it is already the scoping key for a guest's own orders. Owner's decision, 2026-09-04: session rooms, and the deviation from the brief's name is recorded here rather than left as a discrepancy.

**A snapshot is a merge, not a replacement.** The socket joins its room during the handshake, so events flow before the `subscribe` ack arrives. An order committed after `listOrders` read the table reaches the client as `order:created` first, and a snapshot that replaces the board wholesale then erases it — permanently, since nothing re-sends it. So the server stamps `serverTime` **before** the read, and `mergeSnapshot` in `apps/web/lib/board-store.ts` starts from the snapshot and keeps whatever the board learned after that moment: a ticket the read never saw, or a newer copy of one it did. Anything older that the snapshot does not carry is genuinely gone.

**A failed subscribe acks `null`.** The ack used to carry `{ orders: [] }` when the read threw, and every client reads a snapshot as the whole truth — so one transient database error emptied every open board at once. `null` says "no answer this time": the board keeps its tickets, says "Couldn't refresh the board. Retrying…" and asks again after 2 s, 4 s, then every 10 s until it gets one; the guest's order page keeps its order and stays quiet. A subscribe arriving less than a second after the last one on the same socket is acked `null` too, which is the throttle: `subscribe` is a socket message and `@fastify/rate-limit` only ever sees HTTP requests.

**State comes from a snapshot, not from a replayed log.** A client emits `subscribe` and the server answers through the ack callback with everything it should currently show — active orders for the restaurant if the principal is staff, the session's own orders if it is a guest — plus the server's clock. That runs on every connect, so a reconnect and a first connect are the same code path and there is no gap to reconcile. Between snapshots, `applyEvent` in `apps/web/lib/board-store.ts` ignores any event whose `updatedAt` is older than the copy it holds, so an event that overtakes another across a reconnect cannot move a ticket backwards.

**Bumps are optimistic and resync when they lose.** Pressing Start moves the ticket immediately and then posts the transition. If the post fails — usually because another screen moved it first and the API answered 409 `INVALID_TRANSITION` with the current status — the board drops the optimistic status, says "Couldn't move #42. It is Cooking now.", and re-subscribes rather than trying to patch its way back to the truth.

**The board finds out it is offline two ways.** engine.io's defaults (a 25 second ping interval and a 20 second timeout) meant a dead board looked live for about 45 seconds — measured — while a cook read tickets nobody could update. The server's heartbeat is now 10 seconds with a 5 second timeout, and the board also listens for the browser's own `offline` and `online` events, which fire immediately and cover the common case of a kitchen tablet losing its wifi. The heartbeat is the backstop for everything the browser does not notice, such as a server that goes away while the network stays up.

**Two deliberate deviations from spec §5.** Both were decided while building and are recorded here so a reader of the spec is not left wondering.

- Sign-in navigates with `window.location.replace(next)`, not `router.replace(next)`. The destination is a server component that reads the session cookie; a client-side navigation reuses the router cache and can render the new page against the old cookie, which lands a freshly signed-in cook back on `/login`. A full document load is what makes the server see the session that was just created.
- The board's columns are `<section aria-label>` wrapping a plain `<ul>`, not the `role="list"` regions §5 asked for. Same accessible outcome — a named region with a list of tickets inside — from the elements that already mean it, and `role="list"` on a `<ul>` is redundant markup that only exists to work around list-style stripping.

**One process, for now.** The Socket.io server uses the default in-memory adapter. Two API instances would each hold their own rooms and a broadcast from one would never reach a board connected to the other. A multi-instance deployment therefore needs the Redis adapter; that is deployment work and is on the backlog for M6.

**The `resolvePrincipal` extraction is withdrawn.** M1's review recommended pulling the cookie-unsign plus `resolvePrincipal` pair into one reusable helper before M3, on the assumption that the socket handshake would have to repeat it. It does not. The handshake reads a token, not a cookie jar, and the token is minted by a route that has already run the normal principal pipeline. There is nothing left to share, so the recommendation is closed rather than carried forward.

## Consequences

- The browser talks to two origins: the web origin for REST through the rewrite, the API origin for the socket. `NEXT_PUBLIC_API_ORIGIN` is what points at the second, and like every `NEXT_PUBLIC_*` it is baked in at build time — the web image must be rebuilt to move the API, which is the same constraint `API_URL` already carries (ADR 0004).
- The API must be reachable from the browser directly, not only from the Next server. Its Socket.io CORS origin is `WEB_ORIGIN`, the same value REST uses, so a wrong `WEB_ORIGIN` now breaks the board as well as sign-in.
- One more secret in every environment. `SOCKET_TOKEN_SECRET` is required by `apps/api/src/config.ts` with a 32-character minimum, so a deployment that forgets it fails to boot rather than failing to authenticate.
- `demo:reset` is the only event broadcast to every socket. Everything else is addressed to a room, which is the invariant a reviewer should check first when a new event is added.
- A board that reconnects is cheap but not free: every reconnect runs the active-orders query again, and the faster heartbeat makes reconnects more likely on a flaky network. The one-a-second throttle bounds the worst case per socket; the two-hundred-row limit bounds each query. It is the first thing to reconsider if the board ever holds hundreds of tickets.
- Timers on the board are the kitchen's clock, not the screen's. Each snapshot updates an offset (`serverTime` minus the local clock) that every elapsed time is measured against, so a display nobody ever set the time on still ages tickets correctly. `/kitchen` also passes its render-time clock into the board, so the server's HTML paints real ages instead of `0:00`.
- Because the socket is delivery only, an event arriving out of nowhere cannot corrupt state that the API did not already write. The worst a bad event can do is show a stale ticket until the next snapshot.
