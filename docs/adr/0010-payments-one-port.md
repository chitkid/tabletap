# ADR 0010: Payments through one port, settled once

Date: 2026-09-04
Status: accepted

## Context

M4 has to make an order paid, and it has to do it twice over: once through Stripe Checkout, which is what the master brief names, and once through something that works on a machine with no Stripe keys — which is the machine this project is built on (owner, 2026-09-04). Two ways to pay is the easy half. The hard half is that both must arrive at the same `paid`.

The brief is specific about who may write that status: the webhook. Not the browser coming back from a payment page, not the route that opened the session, not a cook pressing a button on the board. That is not fussiness. A redirect is a URL the guest's own browser followed, and anyone can type a URL; a client-side "I paid" is a claim from the least trustworthy party in the transaction. The provider's signed callback is the only statement about money that came from something holding a secret.

Which leaves the shape of the code. The tempting version is a Stripe module that owns the whole flow — create the session, receive the webhook, mark the order paid — and a second, simpler demo module beside it that skips to the end. It is less code and it is a trap: the demo path would then exercise none of the logic that carries production. Every property worth having in a payment flow — the idempotency guard, the amount check, the transaction that moves the order and the payment row together, the broadcast after the commit — would be written once, tested against Stripe fixtures, and never actually run on this machine. The demo would prove that the demo works.

There is also a Fastify detail that shapes the boundary. A signature covers the bytes the provider sent, not the object a JSON parser rebuilt from them, so the webhook route must receive its body as a `Buffer`. Overriding the content-type parser is easy; doing it globally would silently hand every other route a Buffer instead of the parsed body it expects.

## Decision

**One port, two adapters, one settlement.** `apps/api/src/payments/types.ts` declares `PaymentProvider`: a `name`, `createSession(input)` and `readEvent(rawBody, signature)`. That is the entire surface a payment processor is allowed to have inside this API. `createStripeProvider` and `createDemoProvider` implement it; `createPaymentProvider(config)` picks one at boot and `app.payments` is decorated with the result, so no route ever chooses a provider and no route knows which one it has.

`readEvent` returns a `SettleInput` — a provider-neutral description of what happened — or `null`, which means "understood, nothing to do" and is how Stripe's dozens of unrelated event types leave without incident. Everything downstream of that translation is provider-agnostic.

**`settlePayment` is the only writer of `paid`.** It lives in `apps/api/src/lib/payments.ts`, takes a `SettleInput`, and is called from exactly two places: the webhook route and the demo completion route. No other code path in the running app sets `orders.status = 'paid'` — with one deliberate exception, the rush generator, which fabricates a whole paid order in one transaction and is covered by [ADR 0011](0011-demo-payment-provider.md). (A test helper, `payOrder` in `apps/api/src/test/helpers.ts`, writes it directly so an M3-era test can get a cookable ticket without a payment provider; it exists only in the suite.) `paid` appears in no role's `TRANSITION_RIGHTS`, so a member of staff posting a transition to it is refused by the rights check before the state machine is consulted, and the interim `placed → cooking` edge that let M3 cook an unpaid order is gone ([ADR 0009](0009-interim-state-machine.md), closed by commit `d25508a`).

**The `processed_events` row goes in before the work, not after it.** Stripe retries; a webhook that answered slowly, or that answered 500 because the database blinked, will be delivered again. `settlePayment` opens by inserting `(provider, event_id, type, payload, received_at)` into `processed_events`, which carries a unique index on `(provider, event_id)`. A unique violation is not an error — it is the answer: the event has been seen, return `replayed`, do nothing. Inserting first is what makes this a guard rather than a race; a check-then-act would let two concurrent deliveries of one event both pass the check.

**The amount is the database's, twice.** `startPayment` reads `orders.total_cents` and tells the provider what to charge. The route takes no body at all — the order id in the path is the whole request, and the session cookie decides whether that order may be paid — in the same spirit as order placement, where the body contributes menu item ids and nothing that could set a price ([ADR 0006](0006-guest-reads-and-orders.md)). When the event comes back, `settlePayment` compares the amount it carries against the order's total again, because between those two moments the money travelled through a system this API does not control. A mismatch marks the payment `failed`, writes a `payment.mismatch` audit row, and leaves the order unpaid.

Two more checks sit beside it, and both exist because a real provider will eventually deliver something out of order. An event whose order is no longer `placed` is late: the payment row is closed, a `payment.late` row records the status the order actually had, and nothing moves. And both the payment update and the order update name this order — an event carrying a payment id that belongs to a different order rolls the whole settlement back (`ForeignPayment`) and is audited as a mismatch, so one order's session can never pay another's bill.

**The redirect is a hint, and is treated as one.** Stripe's `success_url` is `/orders/<id>?paid=1` and its `cancel_url` is `?paid=0`; the demo terminal returns to the same two URLs. The order page reads that query parameter and nothing else from it: `paid=1` renders "Payment received. Confirming…" _while the order is still `placed`_, and that notice disappears the moment the socket delivers an order whose status is `paid`. The headline, the status badge and the presence of the Pay button all come from the order the server rendered. A guest who types `?paid=1` by hand sees a confirming notice above an order that still owes money, which is the truth.

**The raw-body parser is scoped to the one route that needs it.** `paymentWebhookRoutes` in `apps/api/src/routes/payments.ts` is deliberately _not_ wrapped in `fastify-plugin`. Registered with `app.register`, it gets its own encapsulation context, and the `addContentTypeParser('application/json', { parseAs: 'buffer' })` inside it applies to that context only. The webhook receives bytes; every JSON route outside the scope still receives JSON. This also closes the recommendation carried from M2's review, which asked for precisely this shape.

**The broadcast happens after the commit.** `settlePayment` reloads the order once the transaction has committed and emits `order:updated` into `app.orderEvents`, the emitter [ADR 0008](0008-realtime-delivery.md) put between the domain and the socket. A ticket therefore reaches the board only for a payment the database has already accepted, and the board's New column — narrowed to `paid` alone in `apps/web/lib/board-store.ts` — is a list of orders that were paid for.

**`paidAt` is on the public contract.** `OrderDtoSchema` carries it beside `placedAt`, nullable and required. The guest surface and the e2e budget both measure the wait for the kitchen from the payment rather than from the order, because payment is now what makes a ticket, and the only honest clock for that is the one `settlePayment` stamped.

## Consequences

- Two more secrets, and they travel as a pair. `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET` are both optional in `apps/api/src/config.ts`, and the resolved `config.paymentProvider` is `stripe` only when both are present. Setting one and forgetting the other silently selects the demo provider — the deployment boots, takes no money, and says nothing about it. That is the sharpest edge this decision leaves; a startup warning is on the backlog.
- Swapping providers costs one adapter. Anything implementing `createSession` and `readEvent` drops in behind `createPaymentProvider`, and the settlement, the idempotency guard, the audit vocabulary and the socket broadcast are untouched. The port is small because it was drawn around what two very different providers actually share.
- The demo path is not a mock. `POST /api/payments/demo/complete` builds a `SettleInput` and calls the same `settlePayment` the webhook calls, so the demo run exercises the `processed_events` insert, the amount comparison, the transaction and the post-commit broadcast — the code that would carry a real payment. Whatever the demo proves, it proves about production.
- A mismatched amount answers 200, and that is deliberate. A provider reads any other status as "try again", and an amount that does not match the order will not match it on the retry either. The event is recorded, the payment is closed, the audit log carries `payment.mismatch` with both figures, and the order stays unpaid for a human to look at. The same reasoning covers a late event and an event naming an unknown order.
- Every branch that refuses to pay an order still writes something. `payment.declined`, `payment.mismatch` and `payment.late` are the three, all with the `system` actor and the provider's event id, so "the order was never paid" is always answerable from the audit table rather than from logs.
- A crash between the `processed_events` insert and the settlement leaves an event that is recorded as seen and never acted on: the retry is answered `replayed` and the order stays unpaid. The window is small and the failure is safe in the direction that matters — nobody is charged twice — but it needs a reconciliation pass to close, which is on the backlog.
- One rate limit is now the guest's whole payment budget: `POST /api/orders/:id/payment` allows ten a minute keyed on the signed guest cookie. A guest who opens ten attempts and finishes none has ten pending `payments` rows and no way to open an eleventh for a minute. Attempts are never reaped; also on the backlog.
